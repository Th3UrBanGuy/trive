# TriVE — Vulnerabilities, Workflow Flaws & Missing Pieces

> Comprehensive security audit results. Generated by deep code analysis.
> **6 CRITICAL · 8 HIGH · 10 MEDIUM · 11 LOW · 10 Workflow Flaws · 15 Missing Features · 9 Orphaned Resource Risks**

---

## Executive Summary

TriVE has a solid architectural foundation but several critical security gaps
that must be addressed before any production deployment. The most severe issues
are: an open SSRF proxy in Caddy, a weak `APP_SECRET` fallback that enables
session forgery, a missing upload route, passwords transmitted in URL query
params, and the "zero-knowledge" claim being false (the server can decrypt
all files).

### Top 5 Must-Fix-First

| # | Issue | Impact |
|---|-------|--------|
| 1 | **C-1**: Caddy `XTransformPort` open SSRF | Anyone can proxy to any localhost port |
| 2 | **C-2**: `APP_SECRET` fallback constant | Session forgery, file decryption, admin bypass |
| 3 | **C-3**: False zero-knowledge claim | Server can decrypt all user files |
| 4 | **C-4**: Missing upload route (FIXED) | App couldn't accept uploads — now restored |
| 5 | **C-5/C-6**: Passwords in URL + admin timing attack | Credential leakage + brute force |

## CRITICAL Vulnerabilities

### C-1. Open SSRF via Caddy `XTransformPort` query param
**File**: `Caddyfile:1-13`
```
:81 {
  @transform_port_query { query XTransformPort=* }
  handle @transform_port_query {
    reverse_proxy localhost:{query.XTransformPort}
  }
}
```
Anyone hitting the public server with `?XTransformPort=<port>` gets proxied to
`localhost:<port>`. The mini-service on port 3001 has **zero authentication** and
exposes `/files/download`, `/files/upload`, `/vault/init`, `/auth/send-code`,
`/auth/sign-in`. Internal admin tools (Prisma Studio, etc.) also reachable.
**Impact**: Internal port scanning, unauthenticated access to local services,
full firewall bypass.
**Fix**: Remove the `XTransformPort` block entirely. If needed, restrict to a
known allowlist + HMAC signature.

---

### C-2. `APP_SECRET` fallback makes all crypto and session forgery trivial
**Files**: `src/lib/crypto.ts:16,21`, `src/lib/session.ts:34,44`
```ts
const secret = process.env.APP_SECRET || "telecloud-dev-fallback"
```
If `APP_SECRET` is unset, every session HMAC, MTProto session-string encryption,
and file-chunk key uses a publicly-known constant. Anyone can:
1. Forge a session cookie for any userId
2. Decrypt any `telegramSession` row in the DB
3. Forge admin cookies
**Fix**: Refuse to boot if `APP_SECRET` is unset or < 32 bytes.

---

### C-3. Per-user file encryption key derived from server secret — NOT zero-knowledge
**File**: `src/lib/crypto.ts:20-23,55-72`
```ts
function deriveKey(salt: string): Buffer {
  const secret = process.env.APP_SECRET || "telecloud-dev-fallback"
  return crypto.scryptSync(secret, salt, 32)
}
```
The UI claims "zero-knowledge" and "We never see your Telegram password" but
the file encryption key is derived from a **server-side** secret + per-user salt.
The server can decrypt every file. With C-2, anyone with DB access can too.
**Impact**: False security claim. Malicious operator / DB thief gets all plaintexts.
**Fix**: Implement real client-side key derivation (PBKDF2/scrypt of user password
in browser, never sent to server), OR stop claiming zero-knowledge in the UI.

---

### C-4. Upload endpoint was missing (FIXED)
**File**: `src/app/api/files/upload/route.ts` (now created)
The upload route did not exist — `src/lib/api.ts:67` referenced `POST /api/files/upload`
but no route handler was present. The entire upload pipeline (encrypt, chunk, dedup,
erasure code, manifest) was dead code. The FAB and drag-drop all hit 404/405.
**Status**: ✅ FIXED — upload route created with size (4GB), quota, and folder
ownership checks.

---

### C-5. Share `password` and `email` transmitted as URL query parameters
**Files**: `src/app/api/share/[id]/download/route.ts:42-44`, `src/app/api/share/public/route.ts:29`, `src/lib/api.ts:113-119`
```ts
const password = searchParams.get("password")
const email = searchParams.get("email")
```
Passwords/emails leak to: web server access logs, browser history, `Referer`
header to third-party resources, proxy/CDN caches, service worker caches.
**Fix**: Move to POST body or `X-Share-Password` header. Use `cache: 'no-store'`
and `Referrer-Policy: no-referrer`.

---

### C-6. Admin password compared with non-constant-time `!==`
**File**: `src/app/api/admin/login/route.ts:14`
```ts
if (!password || password !== adminPwd) { ... 401 }
```
String `!==` short-circuits on first differing byte → timing side-channel.
Combined with zero rate limiting (H-1), an attacker can byte-by-byte recover
the admin password.
**Fix**: `crypto.timingSafeEqual(Buffer.from(password), Buffer.from(adminPwd))`.

## HIGH Vulnerabilities

### H-1. Zero rate limiting on every endpoint
**Files**: all of `src/app/api/**`
No per-IP/per-user throttling. Exploitable:
- `/api/admin/login` → unlimited admin password brute force
- `/api/share/[id]/download?password=X` → unlimited share password brute force
- `/api/auth/send-code` → unlimited OTP requests to any phone (Telegram flood-waits the SERVER's API ID, locking ALL users)
- `/api/telegram/vault/scan` → DOS via repeated full-channel scans
**Fix**: In-memory token-bucket per IP+route. Min 5 req/min on auth/admin.

---

### H-2. Share download/view count race (TOCTOU)
**File**: `src/app/api/share/[id]/download/route.ts:62,126,156,171,187,210`
Check-then-increment is not atomic. N concurrent requests all see
`downloadCount < maxDownloads`, all proceed, all increment. Attacker downloads
`maxDownloads × concurrency` copies before limit kicks in. Same for `viewCount`.
**Fix**: Conditional update: `updateMany({ where: { id, downloadCount: { lt: maxDownloads } }, data: { downloadCount: { increment: 1 } } })`, check `result.count === 1`.

---

### H-3. `storageLimitBytes` default 0 (unlimited) and never enforced
**Files**: `prisma/schema.prisma:32`, upload route (now enforces it)
Quota is never checked before upload. Even if admin sets a quota, it had no effect.
**Status**: ✅ Partially FIXED — upload route now checks quota. But admin UI to SET
a quota doesn't exist (F-15).

---

### H-4. Device fingerprint stored but never verified — device binding is theatre
**File**: `src/lib/session.ts:82-120` (createSession), `130-173` (getCurrentUser)
`createSession` writes `telegramApiHash = device:${fingerprint}:${ipHash}:${ts}`
but `getCurrentUser` never reads it back. IP "soft-bind" is also skipped.
A stolen session cookie is fully usable from any device/IP.
**Fix**: Re-derive device fingerprint on every request, compare to stored value,
invalidate on mismatch.

---

### H-5. `telegramApiHash` field overloaded — destroys BYOA credentials
**File**: `src/lib/session.ts:117`
`telegramApiHash` (meant for user-supplied API hash) is overwritten with a device
fingerprint marker on every login, erasing any user-supplied value.
**Fix**: Add a dedicated `deviceFingerprint` column.

---

### H-6. Permissive CORS + credential reflection
**File**: `src/proxy.ts:10-46`
```ts
res.headers.set("Access-Control-Allow-Origin", origin)  // echoes ANY origin
res.headers.set("Access-Control-Allow-Credentials", "true")
res.headers.delete("X-Frame-Options")
```
Any malicious site can make authenticated `fetch()` calls (cookies sent
automatically). Combined with deleted `X-Frame-Options`, app can be iframed
and click-jacked.
**Fix**: Strict origin allowlist. Don't delete `X-Frame-Options`. Only enable
`Allow-Credentials` for routes that need it.

---

### H-7. `dangerouslySetInnerHTML` on mammoth .docx output — XSS
**File**: `src/components/dashboard/file-viewers.tsx:344`
Mammoth is not a security-focused sanitizer. Malicious .docx can carry `<script>`,
`<iframe>`, `onerror=` handlers. A crafted .docx opened in preview/share view
executes script in the TriVE origin → can `fetch('/api/files')` and exfiltrate.
**Fix**: Pass mammoth output through DOMPurify before innerHTML.

---

### H-8. View-only shares do not prevent downloads
**File**: `src/app/api/share/[id]/download/route.ts:66`
```ts
if (share.viewOnly && !inline) { return 403 }
```
`?inline=1` bypasses the check — file served with `Content-Disposition: inline`.
User can right-click → Save As. View-only is illusory.
**Fix**: Server-side rasterization for view-only, OR document clearly that
view-only is a UX hint, not a security boundary.

## MEDIUM Vulnerabilities

### M-1. Share `customSlug` global lookup enables slug enumeration
**File**: `src/lib/share-resolve.ts:67-79`, `src/app/api/share/check-slug/route.ts:42-44`
Bare slug lookup (no `/`) is global. check-slug endpoint returns "Already taken"
for existing slugs. Attacker can enumerate short slugs and access unprotected shares.
**Fix**: Require `username/slug` form. Make check-slug authenticated-only.

---

### M-2. Share public endpoint leaks metadata before password gate
**File**: `src/app/api/share/public/route.ts:51-101,140-153`
Item (file name, size, mimeType, folder tree) is built BEFORE password check.
Terminal states leak `viewCount`, `downloadCount`, `maxViews`, `maxDownloads`,
`expiresAt`. Deleted-state returns `removed: true` before any gate.
**Fix**: Run gate checks before any item enumeration.

---

### M-3. Simulation mode reachable in production via DB tampering
**File**: `src/lib/telegram-service.ts:21-23,97-99,212-237`
`isSimSession()` returns true for `SIM_SESSION_*` strings. If an attacker writes
to `User.telegramSession`, all file ops route through local-disk simulation.
`simStoragePath()` has no path sanitization — `messageId = "../../etc/cron.d/evil"`
writes outside `STORAGE_DIR`.
**Fix**: Strip `/`, `\`, `..` from messageId. Disable sim mode in production
(throw on `isSimSession` when `NODE_ENV=production`).

---

### M-4. `encVerifier` field unused — no encryption key verification
**File**: `prisma/schema.prisma:31`, no references in code
The schema claims "we only store a verifier + salt" but `encVerifier` is never
written or read. No proactive integrity check — decryption just fails at download.
**Fix**: Store HMAC of known plaintext under user-derived key as `encVerifier`.
Check at login.

---

### M-5. `Activity` table grows unbounded; PII not redacted
**File**: `prisma/schema.prisma:190-200`, `src/app/api/auth/sign-in/route.ts:71-73`
Sign-in activity records raw phone number (PII). No TTL, no redaction. Admin
activity endpoint returns raw `details`.
**Fix**: Add retention cleanup. Hash phone numbers. Limit admin view to last N days.

---

### M-6. PATCH `/api/files/[id]` missing destination folder ownership check
**File**: `src/app/api/files/[id]/route.ts:9-26`
No ownership check on destination `folderId`. Admin view (`/api/admin/files`)
queries with `where: {}` (no userId filter) → user A's file appears in user B's
folder tree in admin view.
**Fix**: Verify `folder.userId === user.id` if `folderId` is non-null.

---

### M-7. Manifest rename can resurrect stale names on vault scan
**File**: `src/lib/file-ops.ts:554-601,417-462`
If a rename manifest post fails silently, the old manifest remains "newest" and
a scan resurrects the old name. User thinks they renamed, but next-device login
reverts.
**Fix**: Store explicit `manifestVersion` field, conflict-resolve by version.

---

### M-8. ZIP entry names not sanitized for path traversal
**File**: `src/lib/file-ops.ts:887-906,1041-1058`
File names can contain `..`, `/`, `\`. `archiver.append(buffer, { name: path })`
writes literal entry names. Most extractors strip leading `../` but not all.
**Fix**: Strip leading `/`, replace `..` components with `_..`.

---

### M-9. Session token split fragility
**File**: `src/lib/session.ts:140-142`
`sessionValue.split(":")` breaks if userId format ever contains `:`. Use
`indexOf(":")` + `slice` instead.

---

### M-10. No CSRF protection
**Files**: all POST/PATCH/DELETE routes
Cookies are `SameSite=Lax` (good for forms) but permissive CORS (H-6) +
`Allow-Credentials: true` lets cross-origin `fetch()` bypass SameSite.
**Fix**: Strict CORS allowlist, OR `SameSite=Strict`, OR `X-CSRF-Token` header.
